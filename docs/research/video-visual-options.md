# 视频画面与字幕融合的方案调研

调研日期：2026-10-10。范围：关键帧选择、视觉理解、字幕对齐，以及图文总结的素材准备。核验了官方文档、官方源码和当前项目接口；没有下载视频或模型，没有调用付费 API，没有实测视觉识别质量。本文的采样预算、方案排序和验收标准均是工程建议，不是已有能力或实验结论。

## 建议路线

第一版采用 **本地视频 → 字幕时间线与场景候选 → 少量关键帧 → 宿主视觉 Agent 阅读 → 有来源的画面事实 → 与字幕共同写作 → Markdown 和 HTML**。既有 Agent 若支持读取图片，可以继续用宿主模型额度；CLI 只准备素材，不必立刻新增模型 API。

视觉素材应参与每块字幕的理解和最终内容组织，而不只是写完文字后机械插图。尤其保留字幕没有说出的界面状态、图表变量、板书、实验前后变化和演示结果。文章中的图片也应承担解释或举证作用。

推荐先支持用户提供的本地视频与转录，验证完整链路后再接在线媒体获取。纯文字输入没有真实画面时仍可以使用文章模板，但不能生成冒充视频截图的配图。图片提取、图片理解和文章渲染应分别记录状态，截图成功不意味着已完成视觉理解。

## “图文”与“视频理解”的能力边界

| 路径 | 输入和可补充的信息 | 主要限制 | 项目适用性 |
|---|---|---|---|
| 时间点截图后插入 | 时间戳、字幕、截图；方便读者对照 | 模型可能完全没有读取图片，不应声称视觉理解 | 可作明确标注的低成本降级 |
| 稀疏帧 VLM | 截图、显式时间标签、附近字幕；界面、文字、图表、静态状态 | 无法可靠恢复采样间的短事件、运动轨迹和因果 | 第一版默认候选 |
| 按时间排序的短帧序列 | 连续片段的多帧和时间间隔；比较状态变化 | 仍是采样，非连续全帧感知；不能凭两张图断言中间过程 | 对操作、实验、动作片段按需加密 |
| 视频专用输入 | 文件或公开视频 URL；具体模型可联合音频、视觉和时间轴 | 内部也可能抽帧，受模型、上下文、采样、网络和费用限制 | 补充复杂动态内容的可选适配器 |

这张表是接口和信息覆盖的工程分类。“上传视频文件”不等于观看了原始帧率的全部画面。动作结论需要片段证据；稀疏图片能支持的只是采样时刻可见的事实。

## 关键帧工具

### FFmpeg：最小依赖的候选生成

`select` 可用 `scene` 分数选帧；官方示例为 `gt(scene,0.4)`。`thumbnail=n` 在每批连续的 `n` 帧中挑代表帧，默认批量 100；它不是语义重要性模型。`showinfo` 可输出帧的 `pts_time`（秒）。[FFmpeg select](https://www.ffmpeg.org/ffmpeg-filters.html#select_002c-aselect)、[thumbnail](https://www.ffmpeg.org/ffmpeg-filters.html#thumbnail)、[showinfo](https://www.ffmpeg.org/ffmpeg-filters.html#showinfo)

候选命令示意，未执行；先创建空输出目录，输出帧与日志需要进一步解析和建立索引：

```bash
ffmpeg -i input.mp4 -an \
  -vf "select='gt(scene,0.4)',showinfo,scale=1280:-2" \
  -fps_mode vfr 'frames/scene-%05d.jpg' 2> frames/scene.log
```

工程上不要只保留跳变画面：口播可能长期没有切镜，课件翻页或代码编辑也不一定形成高分切镜。建议合并三类候选：场景变化、字幕中的演示/图表/结果时间点、周期性补采样。避开过渡、黑屏和模糊画面，对候选做去重，再按章节覆盖和视觉价值控制总数。这里的“关键帧”指摘要重要画面，与编码器 I-frame 的术语分开。

### PySceneDetect：需要镜头区间时更合适

`ContentDetector` 根据 HSV 像素变化检测切镜；`AdaptiveDetector` 使用滚动平均，能缓解快速相机运动造成的误检。`SceneManager.get_scene_list()` 返回镜头起止时间。[检测器文档](https://www.scenedetect.com/docs/latest/api/detectors.html)、[SceneManager 文档](https://www.scenedetect.com/docs/latest/api/scene_manager.html)

相比只取切镜边界，镜头区间便于选择中段稳定画面，或从同一镜头提取前/中/后状态。代价是增加 Python 与视频解码依赖。建议先用 FFmpeg 打通低成本链路；当镜头切分、镜头代表帧或参数调优有明确价值时，再增加 PySceneDetect。两种工具都不直接知道“这张图对文章是否有帮助”。

## 视觉模型方案

### 宿主视觉 Agent / OpenAI 图片输入

OpenAI 官方图片接口支持多图片以及 URL、Base64 或文件 ID 输入；图片计入 token。官方列出小字、图表、定位和描述准确性的限制，且模型不会读取图片原始文件名/元数据。[图片输入及限制](https://developers.openai.com/api/docs/guides/images-vision)

本项目若使用宿主读图，应在每张图旁明确给出 `frame_id`、源时间戳及对应字幕，不让模型从文件名猜时间。先生成图像事实，再做字幕融合，可以定位错误来自识图还是写作。图片存在磁盘上、Markdown 引用了图片，均不能作为模型已读图的证据。宿主不支持读图时只能降级到“时间插图”，或由显式配置启用 VLM 适配器。

画面密集的小字号课件建议保留原图，并允许局部放大二次识别。不要把所有候选缩成一张小 contact sheet 后期待完整 OCR。宿主额度不是免费计算；独立 API 模式还需要自己的模型、端点、鉴权、超时、重试和预算设置。

### Gemini：联合音频与时间轴的云端备选

当前官方视频指南说明：默认静态模式抽取 1 FPS 画面并处理音频；支持 `MM:SS` 引用、自定义 FPS 和裁剪。1M 上下文在低/高分辨率约对应最长 3/1 小时，实际还受其他输入占用影响。静态模式约 100/300 token/秒（低/高）；快动作可能遗漏。指定模型另有按需探索时间轴的 agentic 模式。支持公开 YouTube URL；不能据此认为支持 B站页面 URL。[Gemini 视频指南](https://ai.google.dev/gemini-api/docs/video-understanding)

上述参数对应调研时文档，不应把静态预算套给 agentic 模式，也不应把长上下文宣传当作所有账号、模型或输入的时长保证。建议适配器按实际模型能力选择参数，保存处理模式、采样率、裁剪区间和响应 usage；长片按章节分段，在全片时间轴上恢复 offset。

指南内输入大小表与下方 inline 示例仍有 100MB/20MB 的不同描述。接入时应依据所选 SDK/API 的明确规格核验，较大文件采用 File API，避免硬编码一个通用 inline 上限。云端会上传媒体，访问条件和费用应由用户配置决定；本轮没有调用该服务。

### Qwen VL：本地部署备选

调研时 `QwenLM/Qwen2.5-VL` 仓库重定向至 Qwen3-VL。当前官方示例支持本地视频、URL、图像序列及 FPS/帧数/像素预算；视频工具有不同解码后端。Qwen3-VL 强调时间戳对齐，并提供 2B、4B、8B 等规模。[Qwen3-VL 官方仓库](https://github.com/QwenLM/Qwen3-VL)

本地方案可避免新增视觉 API 按次费用，但需要模型存储、运行框架、解码依赖与算力。峰值内存包括权重、视觉输入、KV cache 和解码；帧数、分辨率、上下文、量化和并发都会影响资源，不能只按参数量给出“最低显存保证”。建议先固定一个小规模模型及有限帧预算测内存、耗时和中文课件质量，再决定是否部署。

该 VL 视频路径不应直接宣称理解音轨，音频继续由既有字幕/ASR 提供；同时使用完整视频输入、时间元数据和模型的视频处理器，才可以评估其时间序列能力。无序截图逐张问答仍是稀疏帧模式。不同代际模型和工具参数必须分别固定，不混用 Qwen2.5 与 Qwen3 示例。

## BiliSum 的可借鉴实现

核验固定提交 `fc693b130c6317918ea8fc9143ea824bd21e2114`。README 区分纯文字、时间插图、VLM 理解型三种形式。[BiliSum README](https://github.com/lycohana/BiliSum/blob/fc693b130c6317918ea8fc9143ea824bd21e2114/README.md)

`real.py` 可见流程：先从摘要/笔记规划截图时间点；FFmpeg 提取和 SHA256 去重；`vlm_integrated` 配置可用时逐张发送图片，提取 OCR、事实、重要性等；生成插图计划并重组文章。保存帧索引、视觉上下文、关键帧计划与插图计划。截图时间记录的是请求时间，逐图请求主要提供章节线索。[BiliSum 实现源码](https://github.com/lycohana/BiliSum/blob/fc693b130c6317918ea8fc9143ea824bd21e2114/packages/core/src/video_sum_core/pipeline/real.py)

工程判断：它直接展示了“抽帧 → 理解 → 段落匹配 → 图文文章”的可行代码结构，值得借鉴中间产物与多模式设计；该分支属于稀疏帧理解，不足以证明连续动作理解或完整视频覆盖。当前默认少量帧和逐帧调用也不意味着成本或识别质量最优。本文只检查源码，没有安装 BiliSum、运行真实任务或核验导出质量。

## 与当前项目接合的设计约束

当前 `CommonSubtitleItem` 只有文本、序号和可选起始秒 `s`；`ChatMessage.content` 是字符串；prepare 产出字幕分块清单。因此不能仅在提示词里写“结合视频画面”就完成多模态输入。[当前类型定义](../../src/types.ts)、[prepare 实现](../../src/agent/prepare.ts)

建议保留原字幕，并增加独立的视觉证据文件，由清单关联到字幕块：

```json
{
  "frame_id": "f0008",
  "requested_seconds": 142.0,
  "actual_seconds": 142.08,
  "image": "frames/f0008.jpg",
  "transcript_indices": [31, 32, 33],
  "observation": {
    "visible_facts": ["示例结构，真实任务填写可见事实"],
    "ocr_text": "",
    "uncertainties": []
  }
}
```

以上 JSON 仅是契约示意，时间和内容不是实际视频证据。接入要求：

1. **共同时间轴。** 用源媒体 PTS 记录实际帧时间；请求截图时间与实际帧时间分开。剪辑、音视频分轨或片段分析需保留 offset。当前只有字幕起始时间时，下一条起始点可作近似区间边界，但不能伪装成精确结束时间；无时间戳文稿不能自动声称已对齐。
2. **附近字幕与跨镜头上下文。** 每帧携带所在字幕段及前后上下文；操作/实验需要顺序帧并注明间隔。讲述可能先于或后于演示，不能永远取章节起点当配图。
3. **证据分层。** 原话、可见事实和编辑推断分开。字幕与 OCR 冲突时保留原始两侧证据，标注待核对；VLM 自评 confidence 不当作统计正确率。
4. **内容先行。** 把视觉证据注入字幕块总结，要求新增可见信息，并让关键结论回指字幕范围/帧 ID。最终选图使用同一证据 ID，不能在失败或去重后用数组位置重新匹配。
5. **缓存与降级。** 缓存身份含视频/分P/媒体指纹、采样参数、模型与提示词版本。无媒体、抽帧失败、VLM 不可用、覆盖不足各自明确状态；降级为字幕文章或时间插图时，在结果中如实说明。

建议首轮上限：10–20 分钟样片，约 24 张进入视觉理解、6–10 张进入文章；重点章节至少一个有效候选，对需要动作证据的少量区间加密。数字是实验预算，不能据此宣称足以覆盖所有视频。

## 成本与低成本验收

| 成本项 | 控制方法 | 需记录 |
|---|---|---|
| 在线媒体获取 | 第一版本地输入；后续缓存、限制清晰度/时长 | 文件大小、下载耗时、完整性、平台失败 |
| 抽帧与解码 | 场景候选与字幕候选合并，有限输出 | FFmpeg 版本、总耗时、实际时间戳 |
| 宿主/VLM | 全局与每块帧数上限，缓存视觉事实，按需放大 | 模型、图像尺寸、调用数、usage、失败/重试 |
| 云视频 | 先裁剪重点片段，记录采样/处理模式 | 时长、输入/输出/思考 token、实际账单 |
| 本地模型 | 固定模型/量化/帧预算，先小样本 | 峰值内存、耗时、识图质量与依赖版本 |

不列未经核验的最新 API 单价。预算公式为“实际输入、输出及其他计费 token × 对应供应商价格”，并加上失败重试、重叠分块与媒体传输。静态视频 token 数只能用于该模式的粗估，不能代表最终账单。

优先做三条端到端集成实验，无需围绕每个小函数扩张单测：

| 样片 | 核验目标 | 完成证据 |
|---|---|---|
| 中文课件/代码教程 | 恢复至少两条字幕遗漏的视觉信息，小字可读，图表不添造数字 | 原帧、附近字幕、视觉事实、文章对应段落及人工核对 |
| 操作/实验/运动片段 | 验证稀疏帧遗漏；对重点区间加密后判断顺序和前后状态 | 有时间间隔的帧序列或短片、覆盖说明及错误记录 |
| 口播或素材不足 | 少配图仍有可读文章；无画面/无读图能力时如实降级 | 状态、缺口说明、可打开且无坏图的 Markdown/HTML |

真正完成需要从源字幕与媒体走到最终文章，并检查每张图支持所在段落、时间对应正确、没有虚构画面、视觉新增信息可回溯。B站与 YouTube 的平台适配需各自真实样片验证，不能由本地样片推定成功。
